# ReguAI v0.1 MVP 前端设计与界面详细规格

## 1. 目的与范围

本规格以《ReguAI PRD》为依据，重新定义 v0.1 的前端信息架构、业务交互、权限边界和验收标准，并取代此前将 AI 工作台、文件导入与运维角色独立入口放入 MVP 的设计方向。

v0.1 的目标是让三类业务角色完整处理监管报送闭环：

```text
机构与业务配置 → 数据接收或手工录入 → 校验 → 合规复核
→ 手工或自动报送 → 回执/失败处理 → 日志与审计追溯
```

### 1.1 纳入 v0.1 的能力

- 机构管理。
- 监管业务类型、动态字段、字段必填性、校验规则和报送时限的系统管理。
- A01/A02 业务实例的上游 REST API 接收结果查看，以及手工新增与编辑。
- 配置版本驱动的动态数据录入表单。
- 规则校验、问题修复、合规复核、手工提交、Quartz 自动提交、失败重试和回执查询。
- 站内通知、业务过程日志、审计日志和系统运行日志。
- 报送人员、合规人员、系统管理员三种角色权限。

### 1.2 不纳入 v0.1 的能力

- Excel/CSV 批量导入与导出式数据接入。
- AI、RAG、知识库、Agent、MCP、Skills 和多智能体界面。
- 独立的 Developer / Operator 角色与独立运维门户。
- 外部通知渠道（邮件、消息队列、企业消息系统）。
- 真实监管机构和真实银行系统的外部集成。

## 2. 核心领域模型与状态机

前端以“报送业务实例”为主对象。每个实例至少关联机构、业务类型、数据来源、字段配置版本、业务日期、报送截止日、校验与复核结论、提交状态、回执和日志。

```text
草稿 / API 已接收
→ 数据已完成
→ 校验中
→ 校验失败 ────────────────┐
→ 待合规复核                │
→ 复核退回 ─────────────────┤
→ 已批准、待提交             │
→ 提交中                     │
→ 报送完成                   │
→ 提交失败 / 被拒绝 ────────┘
→ 重试中 → 提交中
```

校验失败和复核退回均回到数据新增页签。只有校验满足提交条件且合规人员完成批准的实例，才进入“已批准、待提交”。

提交方式不在业务类型配置中预设。手工提交与自动任务共享同一状态门禁：系统只处理尚未“报送完成”、且已批准的实例。完成后不得再次提交。提交页面使用幂等键、提交中禁用和状态刷新避免重复操作；后端状态机与幂等校验是最终约束。

## 3. 用户、角色与权限

| 角色 | 主要目标 | 可执行操作 |
| --- | --- | --- |
| 报送人员 | 管理数据并完成报送 | 查看机构和实例；手工新增/编辑数据；运行校验；查看复核意见；手工提交符合条件的实例；查看回执和业务过程日志 |
| 合规人员 | 审核规则结果与异常 | 查看实例、校验结果、规则、状态和异常；对每一条实例进行批准或退回；填写复核意见；不修改业务数据、不发起提交 |
| 系统管理员 | 配置与追溯平台运行 | 管理机构、业务类型、字段、规则、时限、通知；查看任务和运行异常；查看审计日志、系统日志与业务过程日志；执行高风险配置变更 |

前端菜单和动作按角色隐藏或只读，但不替代后端 RBAC。

## 4. 信息架构与路由

| 一级导航 | 路由 | 说明 | 可见角色 |
| --- | --- | --- | --- |
| 工作台 | `/workbench` | 按截止日、阻断问题、待复核、提交失败聚合待办 | 全部 |
| 报送业务 | `/reporting` | 业务实例列表和筛选 | 全部（按动作授权） |
| 业务实例 | `/reporting/:businessType/:instanceId` | 数据新增、校验与复核、提交三个页签 | 全部（按动作授权） |
| 机构 | `/institutions` | 机构维护与选择 | 报送人员、系统管理员 |
| 通知中心 | `/notifications` | 站内通知记录和已读状态 | 全部 |
| 系统管理 | `/admin/*` | 配置、日志、任务和异常 | 系统管理员 |

系统管理子路由：

- `/admin/business-types`：业务类型与状态。
- `/admin/field-schemas`：动态字段、必填性、说明与已发布版本。
- `/admin/validation-rules`：校验规则。
- `/admin/deadline-rules`：A01/A02 等报送时限规则。
- `/admin/operations`：自动报送任务、异常与重试状况。
- `/admin/notifications`：通知记录管理。
- `/admin/audit-logs`：审计日志。
- `/admin/system-logs`：系统运行日志。

## 5. 页面详细设计

### 5.1 工作台

工作台采用任务优先布局，而非数据看板优先布局。首屏内容按业务风险排序：

1. 已逾期或临近截止日的待提交实例。
2. 含 ERROR 的校验失败实例。
3. 等待合规复核或被复核退回的实例。
4. 提交失败、被拒绝和可重试的实例。

每条待办显示机构、业务类型、实例编号、当前状态、截止日、阻断原因与直达动作。摘要区可显示待校验、待复核、待提交和异常提交的数量，但摘要不能取代待办列表。

### 5.2 报送业务列表

列表支持机构、业务类型、数据来源、状态、截止日和创建时间筛选。表格列包含实例编号、机构、业务类型、来源、当前状态、截止日、最近更新时间和操作。移动端改为卡片，保留状态、截止日和主要操作。

“新建手工录入”创建草稿实例；API 已接收的实例从列表进入，数据页默认只读。列表不提供文件上传入口。

### 5.3 业务实例工作区

详情页头部持续展示实例编号、机构、业务类型、状态、截止日和当前待办。页面固定三个页签：

#### 数据新增

- 手工实例按已发布字段配置版本渲染表单。
- 支持保存草稿、编辑与必填校验；保存时保留用户输入和字段级错误。
- API 接收实例默认只读，避免前端在来源数据上无痕篡改。
- 修改数据后，已存在的校验和复核结论失效，状态回到“数据已完成”。
- 新实例绑定创建时的字段配置版本；以后发布的新版本仅用于新建实例，历史实例继续按原版本显示和校验。

#### 校验与复核

- 报送人员发起校验，展示规则编号、严重级别、字段、当前值、期望值、问题说明和定位入口。
- ERROR 必须修复；WARNING 必须填写处理说明；INFO 仅供参考。
- 校验满足条件后，实例进入待合规复核。
- 合规人员必须对每一条实例作出“批准”或“退回”结论；退回必须填写原因。
- 复核意见、复核人和时间在本页可见；完整审计日志不在本工作区显示。

#### 提交

- 仅“已批准、待提交”的实例显示“立即提交”。
- 页面展示截止日、提交状态、尝试记录、失败原因、监管方回执和可用重试操作。
- 手工提交要求二次确认；提交中禁用所有重复提交动作。
- 自动任务对满足同一状态条件的实例提交；前端显示任务结果和下一步动作。
- 报送完成后保留回执和历史，不再显示提交或重试动作。

### 5.4 机构管理

系统管理员可创建、编辑、启停机构；报送人员可检索并选择机构。页面提供编码/名称搜索、状态和类型筛选、分页、详情抽屉及唯一性错误反馈。停用和删除属于高风险操作，须二次确认并写审计日志。

### 5.5 系统管理

业务类型、字段、规则和时限均在系统管理中维护。字段与规则编辑采用“草稿 → 校验 → 发布”流程；发布前显示影响说明，发布后生成不可变版本。高风险修改需二次确认、版本说明和审计记录。

“运营与异常”展示自动报送任务、失败任务、重试状态和系统异常摘要；它是系统管理员功能，不创建独立运维角色。

### 5.6 通知与日志

站内通知覆盖：校验失败、复核退回、临近截止日、提交失败、监管方拒绝和重试耗尽。

日志分为三类：

| 类型 | 内容 | 查看位置 |
| --- | --- | --- |
| 业务过程日志 | 数据录入、校验、复核、提交、重试与回执的状态轨迹 | 实例详情的提交页和系统管理 |
| 审计日志 | 操作人、动作、资源、资源 ID、请求 ID、时间、变更前后值 | 系统管理，仅系统管理员 |
| 系统运行日志 | 自动任务、接口失败、异常摘要与任务重试 | 系统管理，仅系统管理员 |

## 6. 视觉与交互规范

整体采用“稳健监管风格”：深蓝导航、暖白内容区、低饱和蓝色主操作和严格的状态色，避免消费级渐变、玻璃拟态、营销式大标题与 AI 助手式装饰。

| 设计项 | 规范 |
| --- | --- |
| 导航 | 深蓝；清晰分组；按角色动态可见 |
| 内容区 | 暖白/浅灰背景；任务与表格优先 |
| 主操作 | 克制蓝色，仅用于可执行主动作 |
| 状态 | ERROR、WARNING、SUCCESS 同时显示文字、图标和颜色 |
| 风险动作 | 使用确认弹窗，说明影响与不可逆性 |
| 表格 | 桌面显示关键业务列，移动端卡片化 |

响应式断点：

- **≥1024px**：完整导航，表格与详情可并列。
- **768–1023px**：侧边栏收为图标，非关键表格列进入详情。
- **<768px**：导航进入抽屉；实例列表卡片化；动态表单单列；工作区页签以分段切换呈现。

可访问性要求：可见标签、键盘操作、焦点管理、抽屉/弹窗 Esc 关闭、状态不只依赖颜色、字段级错误与全局错误均可读。

## 7. 前端架构与接口边界

采用 Vue 3、TypeScript、Vite、Vue Router、Pinia 与 Element Plus。模块按业务域拆分：

- `session`：Token、用户、角色和单次刷新状态。
- `ui`：主题、导航收起、临时反馈。
- `reportingContext`：机构、业务类型和周期上下文。
- `reportingInstance`：实例列表、详情、数据和配置版本。
- `validationReview`：校验批次、问题、处理说明和复核结论。
- `submission`：提交状态、回执和尝试记录。
- `notifications`：站内通知。
- `adminConfig`、`operations`、`logs`：系统管理域。

浏览器仅经 Gateway 访问后端。统一客户端附加授权与请求 ID，归一化成功、字段错误、业务错误、网络错误与分页响应。具体 API 路径和字段以已发布后端合同为准；本规格不虚构尚未确认的接口。

Token 刷新失败时清除会话并回到登录页。网络/系统错误提供重试与 requestId；业务错误保留用户输入；加载状态禁用重复操作并显示明确反馈。

## 8. 验收与测试

### 8.1 MVP 验收场景

1. API 接收或手工录入数据 → 校验 → 合规复核批准 → 手工/自动报送 → 成功回执。
2. 校验失败 → 定位字段 → 修复 → 重校验 → 合规批准。
3. 提交失败 → 查看失败原因与日志 → 符合条件时重试 → 成功或继续通知。
4. 重复提交请求 → 前端阻止重复动作，后端只产生一次实际报送。
5. 管理员发布字段/规则新版本 → 新实例使用新版本，历史实例保持原版本和可追溯性。

### 8.2 自动化测试重点

- 路由守卫和角色可见性。
- 动态表单按字段配置版本渲染。
- 数据变更导致校验与复核结论失效。
- ERROR/WARNING 门禁、复核批准/退回和提交状态迁移。
- 幂等提交、失败重试、自动任务结果和回执展示。
- 通知、审计日志与系统运行日志的权限边界。
- 键盘操作、焦点管理、状态文字和移动端布局。

## 9. 与 PRD 的可追溯性

| PRD 目标 | 前端设计响应 |
| --- | --- |
| 业务类型配置化与数据物理隔离 | 动态字段版本、业务类型上下文和 A01/A02 实例工作区 |
| 可靠报送 | 状态门禁、强制复核、幂等、重试、回执和任务异常 |
| 报送时限 | 工作台任务优先排序、截止日可见、自动任务和逾期通知 |
| 可审计性 | 业务过程、审计与系统运行三类日志 |
| MVP 边界 | 排除 AI、外部通知、文件导入与独立运维角色 |
